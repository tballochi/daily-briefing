My CI was green for twelve days while the job failed every morning

Timoté Ballochi · September 2026

Every morning a GitHub Actions job researches the news and emails me a briefing. Last Saturday I opened the Actions tab for an unrelated reason and found twelve consecutive green checks, covering twelve mornings on which no briefing had been sent.

It had been broken since August 17. The job caught its own error, emailed me an alert, and exited 0. GitHub rendered a green check for each one.

I had built the failure notification and then stopped reading it, because an alert you receive every morning is an alert you stop seeing. The signal I actually looked at, the green check, was lying to me the whole time.

Here is the bug, the deeper mistake underneath it, and the free serverless setup it all runs on.

The bug: a model name I had hardcoded

One morning I got this instead of my briefing:

Reason: Error code: 404 - {'error': {'message': 'The model
`llama-3.3-70b-versatile` does not exist or you do not have access to it.',
'code': 'model_not_found'}}

Groq had retired the model. I'd hardcoded the name, so every call 404'd and the agent was dead until I noticed.

The lesson isn't "use a different model". It's that a hardcoded model name is a time bomb with someone else's fuse. The model now lives in config with a fallback chain:

model: openai/gpt-oss-120b
model_fallbacks:
  - openai/gpt-oss-20b
  - qwen/qwen3.8-27b

and a retirement degrades the run instead of ending it:

def _chat_completion(client, **kwargs):
    """Run a Groq completion, degrading through MODEL_CHAIN if a model is retired."""
    global _active_model

    for index in range(_active_model, len(MODEL_CHAIN)):
        model = MODEL_CHAIN[index]
        try:
            response = client.chat.completions.create(model=model, **kwargs)
        except Exception as exc:
            if not _is_model_unavailable(exc):
                raise
            logger.warning("Groq model %r is unavailable: %s. Falling back.", model, exc)
            continue

        if index != _active_model:
            logger.warning("Now using fallback model %r for the rest of this run", model)
            _active_model = index
        return response

    raise RuntimeError("Every Groq model in the fallback chain failed as unavailable")

Once a model is known dead, _active_model advances so the rest of the run doesn't keep paying for the same 404. Only when the entire chain is gone does the run fail, and the error then names every model it tried.

If you're building on a hosted LLM API: put the model name in config today, before you need to.

The mistake behind the mistake

Here's the part that actually stings. When I went to verify the fix, I looked at the Actions history and found twelve consecutive green checks, while the briefing had not been sent once since the model was retired.

The job was exiting 0 on failure:

    try:
        _build_and_send()
    except Exception as exc:
        logger.exception("Retry also failed: %s. Sending failure alert.", exc)
        send_failure_alert(str(exc))
        # ...and then nothing. The function returns normally, the process exits 0,
        # and GitHub renders a green check for a morning that never happened.

I'd written a failure-alert email and treated that as the notification channel. But an email you get every morning is an email you stop reading, and the signal I actually check the green check in the Actions tab, was lying to me. The alert fired twelve times and I noticed on day twelve.

The fix is one line, raise after the alert, so the run goes red. The lesson is bigger than the line: a handled error that leaves your status green isn't handled, it's hidden. If you catch an exception at the top level of a scheduled job, make sure the thing you actually look at still turns red.

The whole architecture

There isn't a server. There isn't a container, a database, or a process that stays on.

A free external cron service sends one HTTP request each morning. That request triggers a GitHub Actions job in my own repo, which installs Python, injects my API keys from repo secrets, runs the agent for a few minutes, sends the email, and commits its de-duplication state back into the repository.

The two pieces are often confused, so to be explicit: the pinger only knows how to send an HTTP request. It can't run code, hold secrets, or store anything. GitHub Actions is the machine that does the actual work. The pinger just tells it when.

Everything sits inside free tiers: Groq's free API, Tavily's free search (1000 searches a month; a daily run uses about 180), free Actions minutes on public repos, and a free cron job. There's no paid step in the design and no point where it starts asking for a card.

The agent loop

This is a tool-using loop, not an RSS pipeline. The model gets two tools:

TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "search_news",
            "description": (
                "Search the web for recent news (last 7 days) on a query. Returns a "
                "list of articles with title, url, snippet, date and an already_sent flag."
            ),
            "parameters": {
                "type": "object",
                "properties": {"query": {"type": "string"}},
                "required": ["query"],
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "finalize_selection",
            "description": "Submit the chosen articles once strong, non-duplicate stories are found.",
            "parameters": {
                "type": "object",
                "properties": {"urls": {"type": "array", "items": {"type": "string"}}},
                "required": ["urls"],
            },
        },
    },
]

The model decides what to search for, reads what comes back, and decides whether it needs another search or is ready to commit. It rejects index pages and round-ups, which turn up constantly in news search and are worthless in a briefing.

Two details make it behave:

Every result is tagged with whether it's already been sent.

results.append({
    "title": title,
    "url": url,
    "snippet": (item.get("content", "") or "")[:500],
    "date": item.get("published_date", ""),
    "already_sent": history.is_seen(url, title),
})

The model can see its own past output and route around it. Matching is on both normalised URL and normalised headline, because the same story gets syndicated under different links.

And there are hard caps. Six searches, ten loop steps. An agent left to its own devices will happily burn a free tier exploring.

Two passes, not one

This is the design decision I'd most defend. Research and writing are separate LLM calls with separate system prompts.

The research pass only selects URLs. The writing pass never sees the internet. It gets the real snippets and is told to summarise those and nothing else:

SYNTHESIS_SYSTEM = (
    "You are a technology journalist. You write concise, factual news-brief summaries "
    "grounded ONLY in the source snippet provided for each article. Professional, "
    "neutral tone. No filler, no opinion, no advice, no targeting of any reader."
)

When I had this as one combined call, it drifted into inventing plausible-sounding detail almost immediately, filling gaps with things that sounded right. Splitting the passes fixed it, because the writer has nothing to invent from.

Making hallucinated links structurally impossible

Prompting a model not to invent URLs is not a solution. So the agent's selection gets intersected with the URLs that actually appeared in search results:

by_url = {_norm_url(a["url"]): a for a in collected if a.get("url")}

for url in urls:
    article = by_url.get(_norm_url(url))
    if not article:
        logger.warning("Dropped fabricated/unknown URL from selection: %s", url)
        continue
    ...

If the model invents a link, it isn't in collected, so it's dropped before it can reach the email, and the shortfall is backfilled from real results. It doesn't matter how convincing the fabrication is. It never survives the filter.

Links are then checked for a 404 before they go out, treating only a clear 404/410 as dead so a bot-blocking 403 doesn't cost me a good article.

The other thing I got wrong: trusting GitHub's cron

I originally used GitHub's built-in schedule: trigger. On a low-activity repo it is genuinely unreliable: it delayed runs by hours and dropped some entirely. "Before 10am" wasn't a promise I could keep.

The fix is a free external cron service that calls the workflow_dispatch API at a fixed time. GitHub's own cron stays on as a backup, which means the job can now fire several times in a morning, so it needs to be safe to run repeatedly.

Two guards handle that. A window guard in the workflow:

H=$(TZ=Europe/Paris date +%H)
case "$H" in
  06|07|08|09|10|11) echo "run=true"  >> "$GITHUB_OUTPUT" ;;
  *)                 echo "run=false" >> "$GITHUB_OUTPUT" ;;
esac

and a once-a-day idempotency check in Python:

today = _paris_today()
if not force and history.last_sent_date() == today:
    logger.info("Briefing already sent today (%s) — skipping.", today)
    return

Several triggers, one email, and nothing can wake you at 3am.

State without a database

De-duplication needs memory, and I didn't want to provision storage for a JSON file. So the workflow commits it back to the repo:

git add data/history.json
git commit -m "chore: update article history [skip ci]"
git push origin HEAD:main

It's a hack, and I like it. There's nothing to back up, nothing to pay for, and I can read my own briefing archive in the git log. The push retries with a rebase, because concurrent triggers can leave the runner behind origin/main.

The thing I should have built first

--dry-run. It runs the entire pipeline (research, writing, HTML rendering) and then prints the briefing and writes the rendered email to a file instead of sending it. No email is sent, no history is recorded.

python main.py --dry-run

It needs only a Groq key and a Tavily key. No Gmail App Password, no 2FA, no deploy.

I added it late, and it immediately became the thing I point people at. Configuring email before you know whether you like the output is a ridiculous thing to ask of someone. Every project that produces output should have a mode that shows you the output and does nothing else.

Try it

git clone https://github.com/tballochi/daily-briefing.git
cd daily-briefing
pip install -r requirements.txt

echo "GROQ_API_KEY=..."   > .env     # free: https://console.groq.com/keys
echo "TAVILY_API_KEY=..." >> .env    # free: https://app.tavily.com

python main.py --dry-run

Then edit config.yaml. Topics are free text, so point it at finance, climate, football, your industry, whatever you want to wake up informed about.

Honest limitation to close on: summaries are only as good as the search snippet behind them. When a source returns a thin snippet, the summary is thin. It won't fabricate to compensate, but it doesn't fetch full article bodies yet either. That's the next thing.
